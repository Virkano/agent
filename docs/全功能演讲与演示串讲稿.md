# 线上营销智能体平台全功能演讲与演示串讲稿

版本日期：2026-09-28

## 1. 这场演讲要讲清楚什么

不要把平台讲成一组彼此独立的菜单。整场演讲只讲一条业务主线：

> 围绕同一个客户和同一项营销任务，平台先准备模型、知识和工具，再生成个性化推荐并完成智能对话与营销触达；业务结果进入质检、指标、告警、派单和分析报告，复杂任务通过事件编排和资源协调执行，正式变更前再用故障预演验证，最后由权限、审计、安全和容器化能力保证整套系统可治理、可追溯、可交付。

可以用一句更口语化的话开场：

> 我们不是只做了一个聊天机器人，而是把“数据和知识怎么准备、模型怎么服务、客户怎么推荐和触达、效果怎么监控、异常怎么处置、变更怎么演练、系统怎么交付”串成了一条完整链路。

贯穿演示的对象建议固定为：

- 一个工作空间；
- 一名脱敏演示客户；
- 一项套餐或营销产品；
- 一个营销活动；
- 一个营销任务；
- 一个知识库；
- 一个智能体；
- 一次推荐、对话、触达和反馈；
- 一条指标异常、告警和工单；
- 一个预演场景。

这样每切换一个页面，都能回答“上一环节产生了什么、这一页为什么要用、下一环节会消费什么”。

## 2. 先介绍五类使用角色

| 角色 | 主要使用功能 | 什么时候使用 |
| --- | --- | --- |
| 平台管理员 | 用户、工作空间、角色、资源授权、系统设置、操作日志 | 初始化平台、分配权限、审计操作时 |
| AI 与知识工程人员 | 模型、知识库、工具、智能体、模型生命周期、ETL、检索评估 | 准备问答和推荐能力、更新知识或模型时 |
| 营销运营人员 | 营销场景、活动库、营销任务、客户名单、推荐引擎、触达与转化 | 设计营销活动并执行客户运营时 |
| 质检和值班人员 | 服务助手复核、对话质检、运营监控、指标预警、全局铃铛、AI 报告 | 发现风险、处理告警、复盘效果时 |
| 调度、变更与演练人员 | API 编排、事件编排、资源协调、IVR、变更控制、故障预演 | 接外部系统、执行复杂流程、上线或割接前验证时 |

需要分账号接力演示时，直接使用 [按角色分批演示手册](演示角色稿/README.md)，其中已为五个演示账号分别准备可照读讲稿。

演讲中应反复强调：不同角色看到的是同一条事实链，不是各自维护一份互相矛盾的数据。

## 3. 推荐演讲时长与节奏

### 3.1 完整版本：45～60 分钟

| 环节 | 建议时长 | 核心问题 |
| --- | ---: | --- |
| 开场与首页 | 3 分钟 | 平台解决什么问题 |
| 模型、知识、工具和智能体 | 10 分钟 | AI 能力如何准备并安全输出 |
| 营销活动、任务和推荐 | 12 分钟 | 如何找到客户、推荐内容并完成触达 |
| 质检、监控、告警和报告 | 10 分钟 | 如何发现问题并形成处置闭环 |
| API、事件和资源编排 | 7 分钟 | 多系统、多任务如何可靠执行 |
| IVR、变更和故障预演 | 10 分钟 | 正式上线前如何模拟和控制风险 |
| 权限、安全与部署 | 5 分钟 | 如何治理和交付 |
| 总结 | 2 分钟 | 回扣全链路价值 |

### 3.2 精简版本：15 分钟

精简演示只走七个页面：

1. 首页；
2. 知识库；
3. 智能体；
4. 推荐引擎；
5. 营销任务；
6. 运营监控与全局铃铛；
7. 故障与场景预演。

每页只讲输入、输出和下游去向，不现场创建复杂配置。

## 4. 完整演讲主线

## 第一幕：先看全局，不从聊天框开始

### 第 1 步：首页——先回答“平台现在运行得怎么样”

什么时候用：首页用于登录后的每日总览、演示开场和管理者查看全局状态。

现场展示：

- 当前工作空间；
- 智能体、知识库、工具等资源概况；
- 最近业务和运行状态；
- 右上角全局告警铃铛。

建议讲法：

> 登录后首先看到的不是一个孤立机器人，而是整个工作空间的资源和运营状态。右上角铃铛是全平台统一通知入口，指标告警、营销工单、报告生成、人工节点等消息都在这里收口。

转场：

> 接下来先看这些业务能力是怎么被生产出来的。顺序是模型、知识、工具，最后组装成智能体。

### 第 2 步：系统管理——说明多人、多空间如何隔离

什么时候用：平台初始化、新团队接入、资源授权、审计排查时使用。

现场不必逐页操作，只需要说明：

- 用户和用户组管理人员；
- 工作空间隔离不同项目或业务团队；
- 角色和权限控制谁能查看、编辑、审批、发布；
- 资源管理和资源授权控制智能体、知识库、工具和模型的使用范围；
- 共享资源支持跨工作空间复用；
- 对话用户与认证用于外部聊天端访问；
- 主题、认证、邮件等系统设置提供平台级配置；
- 操作日志记录关键管理行为。

建议讲法：

> 后面看到的每个模型、知识库、任务、报告和预演实例都有工作空间边界。管理员负责资源和权限，业务人员只在授权范围内操作。

## 第二幕：把 AI 能力准备好

### 第 3 步：模型——选择模型、验证模型、管理版本

什么时候用：首次接入模型、更换供应商、配置 Ollama、训练新推荐模型或评估发布版本时使用。

现场展示：

- 模型供应商和模型列表；
- LLM、Embedding、Reranker 等模型类型；
- Ollama 基础地址和模型连通性；
- 模型生命周期中的实验、评估、发布和历史记录；
- 自动训练流水线的阶段、质量门禁、失败重试和发布结果；
- 模型监控中的可用性、时延、效果和告警。

建议讲法：

> 大模型负责生成回答，Embedding 负责把资料和问题转换成向量，Reranker 负责把候选结果重新排序。平台把“模型能调用”和“模型适合上线”分开管理：连通性测试只证明服务在线，生命周期和评估才决定哪个版本可以发布。

什么时候选什么：

- 普通对话生成：使用 LLM；
- 知识库检索：使用 Embedding；
- 候选很多且需要提高前几名质量：增加 Reranker；
- 本地开发和数据不出域：使用本地 Ollama 或容器内向量服务；
- 正式上线：使用经过评估和发布的模型版本。

转场：

> 模型有了以后，还不能直接回答企业问题，因为模型不知道我们的产品、规则和最新资料。下一步要建设知识库。

### 第 4 步：知识库——把资料变成可检索、可版本化的知识

什么时候用：导入产品手册、营销政策、服务规范、FAQ、制度文件，以及资料更新或检索效果变差时使用。

建议按下面顺序展示：

1. 创建知识库并绑定 Embedding 模型；
2. 上传文档或导入资料；
3. 查看文档、分段和问题；
4. 使用自定义分段和术语库调整专业词；
5. 运行命中测试；
6. 在检索评估中批量检查召回、精排和答案依据；
7. 在 ETL 与索引版本中查看处理阶段、质量门禁、发布和回滚；
8. 必要时通过知识库工作流做清洗和加工。

建议讲法：

> 文档上传不是终点。平台会保留原文、分段、向量索引和版本。命中测试用于快速看一个问题能不能搜到资料；检索评估用于成批比较召回和精排效果；ETL 与索引版本用于正式发布和出现问题时回滚。

什么时候用什么：

- 临时检查单个问题：命中测试；
- 系统性验证检索质量：检索评估；
- 资料更新上线：ETL 与索引版本；
- 分段不合理：文档分段或知识库工作流；
- 专业名词识别不准：术语库；
- 新版本效果退化：回滚到历史索引版本。

转场：

> 知识库解决“知道什么”，工具和 API 解决“能做什么”。

### 第 5 步：工具与 API 编排——让智能体调用业务能力

什么时候用：智能体需要查数据库、调用搜索、连接业务系统、接入晓搭或组合多个接口时使用。

工具页面重点：

- 管理内置工具、自定义工具和工作流工具；
- 配置输入字段和初始化参数；
- 把工具授权给指定工作空间或智能体；
- 通过工具工作流组合多个能力。

API 编排与晓搭页面重点：

- 登记 API 资产和输入、输出 Schema；
- 导入 OpenAPI 3.x 契约；
- 使用 REQUEST、CONTEXT、CONSTANT、PREVIOUS_OUTPUT 四类参数来源；
- 校验未知依赖、自依赖和环路；
- 创建不可覆盖的新契约版本；
- 比较版本差异和破坏性变更；
- 按测试、灰度、生产环境发布；
- 配置超时、重试和熔断；
- 查看脱敏调用审计。

建议讲法：

> 工具适合给智能体直接使用，API 编排适合把外部系统能力治理成版本化契约。平台不保存真实 API Key，只保存凭证引用；一次接口修改不会覆盖历史版本，破坏性变更必须确认后才能进入更高环境。

转场：

> 现在模型、知识和工具都准备好了，下一步把它们装配成一个可发布的智能体。

### 第 6 步：智能体——把模型、知识、工具组装成服务

什么时候用：创建客服助手、营销助手、员工助手或流程型智能体时使用。

现场展示：

- 创建智能体并选择类型；
- 配置提示词、模型参数和开场白；
- 绑定一个或多个知识库；
- 开启工具、其他智能体或 MCP 能力；
- 使用高级编排设计工作流；
- 配置访问方式、对话用户和授权；
- 查看对话日志；
- 发布聊天端入口。

建议讲法：

> 智能体是能力装配层。模型决定生成能力，知识库提供企业事实，工具负责执行动作，工作流控制步骤和条件，访问设置决定哪些用户可以使用。

转场：

> 接下来不再停留在配置页，我们让一名客户真正发起问题，看回答如何经过检索、生成、合规和人工复核。

### 第 7 步：客户对话与服务助手复核——回答之前先过安全门

什么时候用：客户通过聊天端咨询产品、政策、办理流程或营销权益时使用。

现场演示三种问题：

1. 正常资料问题：检索到知识片段，生成带引用回答；
2. 无资料问题：走配置的兜底答复；
3. 受控风险问题：发送前合规检查拦截或标记复核。

随后进入“服务助手复核”：

- 查看风险类型和引用数；
- 查看客户实际收到的安全答复；
- 由管理员确认或排除；
- 查看不可覆盖的处理事件。

建议讲法：

> 合规检查发生在流式内容发送之前。审计只保存规则版本、风险类型、引用 ID 和内容哈希，不额外保存命中的敏感原文。人工复核是对机器规则的治理补充。

## 第三幕：进入营销业务主流程

### 第 8 步：营销场景——先定义“为什么营销”

什么时候用：为新产品推广、存量客户升档、流失挽回或重点客群运营定义业务模板时使用。

现场展示：

- 场景名称、目标、客群和渠道；
- 场景关联的智能体、知识和策略；
- 场景状态和复用方式。

建议讲法：

> 场景是营销业务的上层模板，先统一目标和约束，再创建具体任务，避免每次营销都从零配置。

### 第 9 步：营销活动库——管理“给客户什么”

什么时候用：维护套餐、权益、优惠和营销物料，或需要活动审批、灰度和回滚时使用。

现场展示：

- 活动名称、编码、权益、费用和合约说明；
- 适用套餐、省份、用量条件、生效时间；
- 优先级和互斥组；
- 草稿、审批、上线、暂停和归档；
- 不可变版本历史；
- 从历史版本恢复时创建新草稿；
- 活动效果复盘和放量建议。

建议讲法：

> 活动库是可推荐物料的正式来源。版本历史保证任务和会话使用的是当时快照，后续修改不会改写已经发生的事实。

转场：

> 场景说明为什么做，活动说明给客户什么，营销任务则负责什么时候、对谁、通过什么渠道执行。

### 第 10 步：营销任务——组织客户、批次、审批和触达

什么时候用：发起一轮具体营销行动、导入客户名单、灰度触达和追踪结果时使用。

建议按业务顺序展示：

1. 创建任务并关联营销场景；
2. 选择活动版本、智能体和知识库；
3. 设置目标客群、渠道、目标数和首批灰度人数；
4. 导入客户名单并逐行保留异常；
5. 查看客户分层、状态、意向和上下文；
6. 创建触达批次；
7. 提交审批并进入审批待办；
8. 关注审批 SLA 和超时预警；
9. 审批通过后执行灰度触达；
10. 记录已触达、已咨询、有意向、无意向和转人工；
11. 写入转化归因；
12. 复盘批次和任务效果。

建议讲法：

> 客户名单、批次和活动配置都会保存快照。审批人和创建人分离，高风险批次不能绕过审批；触达和转化结果会成为后续推荐增量学习、质检和经营分析的输入。

### 第 11 步：召回与精排推荐引擎——回答“给这名客户推荐什么”

什么时候用：客户和活动较多，需要个性化选品、排序、解释和持续学习时使用。

推荐按技术链路倒着演示结果、正着解释原理：

1. 在“精排 TopN”选择客户，直接看最终推荐；
2. 展开七项可解释特征贡献；
3. 回到“多路融合”，解释六路候选如何去重加权；
4. 查看“TopK 推理”，说明双塔如何从客户和物料向量快速召回；
5. 录入曝光、点击、转化或负反馈；
6. 查看增量学习生成新版本；
7. 在“效果监控”比较 CTR、CVR、负反馈率、覆盖率、多样性和时延。

六路召回包括：

- 双塔模型召回；
- 业务规则；
- 协同过滤；
- 内容相似；
- 全局热度；
- 地域匹配。

建议讲法：

> 双塔解决海量候选中的快速召回，多路融合避免单一模型遗漏，精排负责最终 TopN 和业务约束，反馈再进入增量学习。推荐结果不仅有分数，还有来源和特征贡献，便于运营解释和复盘。

什么时候用什么：

- 候选规模大、需要快速筛选：双塔 TopK；
- 冷启动或模型覆盖不足：多路融合；
- 需要业务规则、活动优先级和可解释排序：精排 TopN；
- 已有曝光、点击、转化数据：增量学习；
- 判断版本能否继续放量：效果监控。

转场：

> 推荐和触达完成后，不能只看发送量，还要看客户实际收到的内容是否合规、效果是否健康。

### 第 12 步：对话质检——控制营销内容质量

什么时候用：营销对话完成后、批次扩大前或发现投诉风险时使用。

现场展示：

- 自动质检规则和命中结果；
- 敏感词、禁答、隐私、引用等风险；
- 人工质检、修订和复核；
- 发送前影子质检和依赖降级；
- 规则效果分析；
- 高风险规则灰度拦截和自动回退；
- 质检结果与活动、任务、会话关联。

建议讲法：

> 普通服务助手有通用发送前合规，营销对话还保留独立的营销质检闭环。规则先影子运行观察误报，再进入灰度拦截；高风险规则效果变差时可以自动回退。

## 第四幕：从执行进入运营闭环

### 第 13 步：营销运营监控——看任务是否健康

什么时候用：运营人员每日看盘、告警值班、负责人绩效和问题复盘时使用。

现场展示：

- 任务健康、目标客户、触达、会话和转化；
- 任务逾期和审批超时；
- 告警级别、状态、SLA 和负责人；
- 工单认领、处理、解决、关闭和转派；
- 负责人工作量、响应时间和处理达标率；
- 重复告警排行、合并排查建议、高频根因；
- 历史处理经验和复发告警。

建议讲法：

> 运营监控回答“任务有没有按计划推进、问题由谁负责、有没有超时、同类问题是否反复发生”。告警不是一个红点，而是带负责人、SLA、处置事件和复盘结论的工单闭环。

### 第 14 步：指标预警中心——从原始观测发现异常

什么时候用：需要监控服务能力、安全隐患、成本效能、客户交付等通用指标时使用。

八类主题：

- 监控排障；
- 安全隐患；
- 成本效能；
- 客户交付；
- 资源能力；
- 服务质量；
- 业务发展；
- 其他管理主题。

现场展示：

- 指标定义和非敏感数据源元数据；
- 采集批次、原始观测和逐行异常；
- 固定阈值和动态基线；
- 规则版本和合规门禁；
- 八类主题趋势与设备、网元、时段筛选；
- 观测、基线、规则、告警和派单详情下钻；
- 值班台历和班次冲突校验；
- 指派、转派、认领、处理、备注、解决和关闭事件链。

建议讲法：

> 指标预警中心从原始观测开始，不直接维护一份容易漂移的报表数据。动态基线只使用当前观测之前的同维度样本；规则每次修改都生成新版本，告警保存命中的规则版本。

### 第 15 步：平台监控——看模型、数据、知识和资源本身

什么时候用：AI 工程和值班人员检查平台基础能力是否健康时使用。

现场展示：

- 模型服务可用性和延迟；
- 数据、知识、索引和资源指标；
- 阈值规则；
- 告警确认和恢复；
- 失败重试与回滚响应任务；
- 告警进入全局铃铛。

区分讲法：

> 营销运营监控关注业务任务，指标预警中心关注通用业务和运维指标，平台监控关注模型、知识、数据和资源底座。三者最终都进入统一告警和通知体系。

### 第 16 步：AI 分析报告——把事实整理成管理结论

什么时候用：日报、周报、专项分析、管理汇报和订阅分发时使用。

现场展示：

- 报告模板；
- 任务、时间范围和统计口径；
- 事实数据计算和来源快照；
- AI 解读、问题归因和建议；
- 报告版本和生成记录；
- 定时订阅；
- 站内通知和多格式导出。

建议讲法：

> 报告不是临时拼一段大模型文字。平台先固化统计范围和来源事实，再生成解读和建议，订阅结果进入全局铃铛；历史报告保留当时快照，不随源数据变化。

转场：

> 到这里业务闭环已经形成。下一部分解释，当事件更多、系统更多、任务会争抢资源时，平台怎么保证流程可靠执行。

## 第五幕：用编排把多个系统和任务串起来

### 第 17 步：事件任务编排——让业务事实自动触发流程

什么时候用：推荐曝光、客户反馈、告警、外部系统事件到达后，需要自动启动串行、并行或人工流程时使用。

现场展示：

- 标准事件契约和载荷校验；
- 事件 ID、幂等键和工作空间边界；
- 流程版本和 DAG；
- 串行、并行、人工复核节点；
- 条件路由、跳过、有限重试、备用路径和失败策略；
- 节点 Trace、Span、输入输出和尝试记录；
- 历史版本重放。

建议讲法：

> 事件编排负责“什么事情发生后启动什么流程”。同一个幂等事件只产生一条运行，流程发布新版本不会改写历史运行。人工节点不会被系统假装完成，而是明确停在待处理状态。

### 第 18 步：资源协调中心——解决任务争抢和并发冲突

什么时候用：多个智能体、训练任务、批量任务或编排节点竞争有限资源时使用。

现场展示：

- 资源池、总配额和单任务上限；
- 任务优先级和等待队列；
- 互斥资源键；
- 持久化租约和过期回收；
- 请求号与幂等键；
- 完成、失败和取消；
- 不可变调度事件。

建议讲法：

> 资源协调负责“流程能不能现在执行”。优先级只排序等待任务，不抢占正在运行的任务；PostgreSQL 保存任务、租约和事实链，Redis 只做可降级优化。

### 第 19 步：触发器——处理定时和外部触发

什么时候用：日报生成、周期扫描、定时同步、Webhook 或外部事件触发智能体时使用。

简要说明：

- 定时触发适合固定时间任务；
- 事件触发适合业务事实到达；
- 外部接口触发适合系统集成；
- 复杂执行过程交给事件编排和资源协调。

## 第六幕：处理电话、变更和故障风险

### 第 20 步：IVR 与变更操作控制

什么时候用：验证电话渠道协议、模拟语音会话，或在割接、发布、配置变更前进行风险控制时使用。

IVR 部分展示：

- 创建脱敏会话；
- HTTP 调用和 WebSocket JSON 契约回放；
- 音频分片、模拟 STT、响应和 TTS 指令；
- 播报、转接、结束等有序事件；
- PostgreSQL 审计事实和 Redis 当前态。

变更控制部分展示：

- 变更输入快照；
- 红、黄、绿风险评估；
- 关键校验失败直接红灯；
- 高风险人工确认绑定具体评估版本；
- 变更前和执行中通信门禁；
- 开始、完成和操作轨迹；
- 周期质量报告和导出。

建议讲法：

> IVR 当前用于协议模拟和消息契约回放，不能宣称真实电话线路已经接通。变更控制则把“风险评估、人工确认、通信告知、执行动作和质量报告”串成可追溯链路。

### 第 21 步：故障与场景预演——在真实事故之前先走一遍

什么时候用：重大营销活动、系统上线、网络割接、应急预案验证、故障培训和复盘取证时使用。

建议按“一次完整预演”的顺序讲，不按页面组件从上到下逐块讲：

1. 从预演场景库选择已发布场景；
2. 创建预演实例并固化模板快照；
3. 生成或导入申告批次，异常行单独保留；
4. 使用数据模拟生成指标或舆情趋势；
5. 构建版本化预演数据模型并检查质量；
6. 绑定故障配置，校验告警、超时、时段、拓扑和预案五项门禁；
7. 启动场景执行，注入申告、趋势和处置流程；
8. 推进公众或政企处置步骤，演示阻塞、恢复、跳过或失败；
9. 触发模拟告警并完成上报、确认和恢复；
10. 调用 API Mock 或原子能力，模拟成功、失败和超时；
11. 通过辅助模拟生成网络、故障和流量因子；
12. 在统一记录中查询实例、批次、流程、告警、调用和回溯事实；
13. 生成数据动态回溯，比较故障窗口前后指标；
14. 生成场景动态回放，查看流量帧、拓扑前后镜像、节点轨迹和 SHA-256；
15. 创建故障上报，推进受理、升级、恢复和关闭，并查看 SLA；
16. 导出 CSV、PDF、Excel 或 JSON 报告。

什么时候用哪个预演能力：

| 需求 | 使用功能 |
| --- | --- |
| 模拟客户集中申告 | 申告模拟 |
| 演练人员处理步骤 | 处置进度模拟 |
| 生成指标或舆情曲线 | 数据模拟与趋势看板 |
| 复用一套演练剧本 | 预演场景库 |
| 固化演练数据结构和血缘 | 预演数据模型 |
| 演示告警产生、确认和恢复 | 告警模拟 |
| 模拟外部 API 成功、失败、超时 | 能力调用模拟 |
| 检查故障前后业务事实 | 数据动态回溯 |
| 播放拓扑和流量变化 | 场景动态回溯 |
| 管理故障配置和预案门禁 | 故障模拟配置 |
| 模拟正式故障申报和 SLA | 故障上报模拟 |
| 批量生成网络、故障、流量数据 | 辅助模拟 |
| 跨类型查询所有模拟事实 | 模拟记录查询 |

建议讲法：

> 预演不是做一段动画，而是生成一套版本化、可回放、可校验的事实链。配置、实例、流程、告警、调用、拓扑和报告都保留当时快照，后续修改模板不会改变历史证据。

## 第七幕：用治理和部署收口

### 第 22 步：全局铃铛——所有待办只从一个入口处理

什么时候用：用户需要集中查看跨模块通知、告警和待办时使用。

说明来源包括：

- 营销告警与工单；
- 指标派单与转派；
- 平台监控告警；
- AI 报告生成；
- 编排人工节点；
- 变更提醒和其他站内通知。

建议讲法：

> 各模块不重复建设通知中心，所有需要人关注的事项统一进入右上角铃铛，再跳回对应业务页面处理。

### 第 23 步：数据、审计和安全治理

什么时候用：项目交付、安全检查、数据盘点、问题追责和上线评审时使用。

需要说明：

- 数据资产目录来自已注册模型，只导出元数据，不查询业务行；
- 接口清单来自实际 URL 树；
- 用户和营销客户直接读取写入最小化审计事件；
- 请求日志不保存查询值、返回内容和真实凭证；
- API、模型和外部系统凭证只保存引用或加密内容；
- 安全扫描区分依赖、镜像和三同步，不把未运行或发现问题说成通过；
- 数据库恢复演练使用隔离临时库，不覆盖源库。

### 第 24 步：单业务镜像交付

什么时候用：开发环境交接、测试环境部署和后续生产发布时使用。

建议讲法：

> 最终只交付一个业务镜像，包含管理端、聊天端、Django、Celery 和本地向量服务，对外只开放 8080。PostgreSQL、Redis 和 Ollama 使用部署方已有服务，通过环境变量接入。初始化 SQL 只创建空业务库和 pgvector，表结构由 Django migrations 自动维护。

展示内容：

- `/healthz` 检查 PostgreSQL、Redis 和容器内向量服务；
- 管理端、聊天端和 API 文档入口；
- 安全环境变量门禁；
- 初始化 SQL；
- 运行和停止命令；
- 日志和故障排查入口。

## 5. 一口气讲完的完整业务链

如果需要不看页面、只用一段话把链路讲顺，可以直接使用下面这段：

> 管理员先创建工作空间、用户和角色并授权资源；AI 工程人员接入大模型、向量模型和精排模型，把产品资料导入知识库，通过 ETL、索引版本和检索评估确认资料可用，再把模型、知识库、工具和 API 组装成智能体。营销运营人员建立营销场景和版本化活动，创建任务、导入客户、分层并提交触达批次审批。推荐引擎先用双塔和多路策略召回候选，再按业务特征精排出 TopN，智能体结合客户上下文和知识库完成对话，发送前经过合规检查，风险回答进入人工复核。触达、点击、转化和负反馈进入增量学习和任务复盘，对话进入自动与人工质检。业务指标、平台指标和任务状态持续进入趋势分析，越界后生成告警、派单和全局铃铛通知，值班人员认领、处置、解决并沉淀根因。管理者通过 AI 分析报告查看同一任务的推荐、触达、告警、工单和编排事实。跨系统动作通过 API 契约、标准事件、动态路径和资源租约可靠执行；涉及电话、发布和割接时先进行 IVR 协议模拟、变更风险评估和通信确认。重大活动上线前再用故障与场景预演生成申告、趋势、告警、流程、能力调用和拓扑回放，验证预案后再发布。最后，权限、审计、安全检查、备份恢复和单业务镜像保证整套系统可以治理和交付。

## 7. 现场演示前准备清单

### 7.1 服务准备

- PostgreSQL 和 Redis 在线；
- Ollama `/api/tags` 返回成功且目标模型已安装；
- 本地向量服务可以完成一次真实 `embed_query()`；
- 后端 `/healthz` 返回 200；
- 管理端和聊天端均可访问；
- Celery Worker 正常连接 Redis。

### 7.2 数据准备

- 使用固定演示工作空间；
- 准备一个脱敏客户和一项产品；
- 知识库至少有一份已索引资料；
- 智能体已绑定正确模型和知识库；
- 活动、任务和推荐策略使用已发布版本；
- 准备正常问答、无资料问答和风险问答各一个；
- 准备一条可展示的告警、工单、报告和预演实例；
- 演示数据明确标记为模拟或验收数据。

### 7.3 页面准备

- 提前登录，确认当前工作空间正确；
- 浏览器按演示顺序打开少量标签页；
- 全局铃铛保留可展示通知；
- 需要打开的抽屉和详情先确认数据存在；
- 不在现场导入大文件或执行耗时训练；
- 不在投屏日志中展示口令、Token、API Key 或客户敏感信息。

## 8. 演讲中必须说明的边界

为避免把粗粒度 V1 演示成已经完成生产联调，结尾必须主动说明：

- IVR WebSocket 当前是 JSON 消息契约回放，不是真实电话线路；
- 晓搭当前完成适配底座、契约、Mock 和治理，真实网关与真实凭证校验仍需外部联调；
- 本地演示使用的向量模型可以验证技术链路，不代表生产语义效果已经达标；
- 模拟触达、意向和转化只证明系统链路，不代表真实客户行为和商业效果；
- 故障、申告、趋势、能力调用和上报属于预演事实，不冒充生产事故；
- 模型训练和知识 ETL 已有本地版本事实，外部 MLflow 等平台仍需按环境联调；
- 安全扫描基线中仍有依赖漏洞和镜像扫描待闭环，不能宣称生产安全门禁已通过；
- 本地恢复演练不等于生产异地灾备和正式 RTO/RPO 达标；
- 性能压测已按开发阶段决策后置，不能宣称建设方案性能指标已经验收。

建议收尾话术：

> 当前版本已经把建设方案中的主要业务能力做成一套可演示、可串联、可追溯的粗粒度 V1。今天展示的是完整业务链和治理机制；真实电话线路、晓搭生产网关、生产语义效果、安全漏洞闭环、异地灾备和性能指标，将在拿到对应外部环境后进入下一阶段验收。
