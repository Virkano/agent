# 第三十三阶段：后台告警扫描与站内通知验收文档

## 1. 本阶段目标

把上一阶段需要人工打开“运营监控”才能同步的告警，升级为后台自动扫描和站内提醒：系统每 5 分钟扫描所有存在营销任务、规则或告警的工作空间；告警首次生成或恢复后再次触发时，为对应工作空间用户生成一条站内通知；用户可从顶部铃铛直接进入准确的告警处理抽屉。

本阶段不改写营销对话、任务执行和质检主流程，扫描失败也不会阻断这些核心流程。

## 2. 用户能看到的变化

登录管理端后，页面右上角新增“营销告警通知”铃铛：

- 红色数字表示当前工作空间、当前用户的未读告警数。
- 点击铃铛可查看最近 20 条告警通知。
- 通知区分“新告警”和“告警重新打开”，并显示告警级别、说明和发生时间。
- 点击通知后自动标记为已读，并进入 `/admin/marketing-operations?alert_id={告警ID}`。
- 运营监控页会按告警 ID 打开准确的处理抽屉，不需要用户再从表格中查找。
- 支持一键“全部已读”。
- 手动点击“同步告警”后，顶部未读数立即刷新；平时每 60 秒自动校准一次未读数。

## 3. 后台扫描机制

调度任务：`marketing_alert_scan`

执行频率：每 5 分钟一次。

执行链路：

```text
APScheduler 定时触发
        ↓
投递 Celery 任务 marketing.scan_all_alerts
        ↓
逐工作空间计算告警指标
        ↓
创建、更新、恢复或重开告警
        ↓
只为“首次创建”和“恢复后重开”生成站内通知
```

可靠性约束：

- 调度器使用项目已有的 Celery worker 启动机制注册，不新建独立常驻进程。
- 注册过程使用 Redis 锁，避免多 worker 重复注册。
- 同一调度任务最多并发执行一次，并合并错过的执行周期。
- 某个工作空间扫描失败时只记录该空间错误，继续扫描其他工作空间。
- 通知以“用户 + 告警操作记录”建立唯一约束，重复扫描不会重复提醒。
- 告警指标普通更新、人工认领、开始处理和关闭不会反复生成通知。

## 4. 通知接收范围

通知按工作空间隔离，接收人按以下顺序确定：

1. 工作空间角色映射中的有效用户。
2. 没有成员映射时，回退到该工作空间营销任务的有效负责人。
3. 默认工作空间仍无人可接收时，回退到有效管理员。
4. 用户手工同步时，当前操作人也会接收到本次应生成的通知。

用户只能查询和操作自己的通知；使用其他用户、其他工作空间或不存在的通知 ID 时不会泄露通知内容。

## 5. 新增接口

```http
GET  /admin/api/workspace/{workspace_id}/marketing/notification/{page}/{size}
GET  /admin/api/workspace/{workspace_id}/marketing/notification/unread-count
POST /admin/api/workspace/{workspace_id}/marketing/notification/{notification_id}/read
POST /admin/api/workspace/{workspace_id}/marketing/notification/read-all
GET  /admin/api/workspace/{workspace_id}/marketing/alert/{alert_id}
```

通知列表可选查询参数：

```text
status=UNREAD
status=READ
```

告警同步接口保持不变，但响应中增加本次新建通知数量：

```http
POST /admin/api/workspace/{workspace_id}/marketing/alert/sync
```

```json
{
  "active_count": 1,
  "notification_count": 1
}
```

## 6. 本地和部署运行条件

前端与 Web 后端启动后，人工“同步告警”和站内通知查询即可使用。

要让每 5 分钟后台扫描真正执行，还需要启动项目原有 Celery 任务服务：

```bash
set -a && source .env.local && set +a
.venv/bin/python main.py dev celery
```

生产部署继续使用项目已有任务服务启动方式：

```bash
.venv/bin/python main.py start task
```

任务服务启动时会自动注册 `marketing_alert_scan`，不需要手工执行初始化脚本。本地数据库迁移 `marketing.0019_marketingnotification` 必须先完成。

## 7. 手工验收步骤

### 7.1 顶部铃铛和通知列表

1. 登录管理端并切换到有营销任务的工作空间。
2. 打开“运营监控”，点击“同步告警”。
3. 确认右上角铃铛出现未读数字。
4. 点击铃铛，确认列表显示告警标题、说明、时间和未读标记。
5. 连续点击“同步告警”两次，确认相同告警操作不会新增重复通知。

### 7.2 通知直达和已读

1. 点击一条未读通知。
2. 确认 URL 出现 `alert_id`，并直接打开对应“告警处理”抽屉。
3. 确认抽屉中的标题、当前指标、负责人和处理记录与通知对应。
4. 关闭抽屉，确认 URL 中的 `alert_id` 被清理。
5. 再次点击同一条已读通知，确认仍能重新打开同一告警。
6. 点击“全部已读”，确认未读数字消失，列表顶部显示“全部已读”。

### 7.3 自动扫描

1. 启动 Celery 任务服务。
2. 确认 `django_apscheduler_djangojob` 中存在 `marketing_alert_scan`，并有下一次执行时间。
3. 准备一项达到阈值但尚未生成告警的营销异常。
4. 等待最多 5 分钟，不手工打开运营监控。
5. 刷新任意管理页面，确认铃铛出现新通知。
6. 再等待一个扫描周期，确认相同事件不会重复通知。

### 7.4 工作空间隔离

1. 在两个工作空间中分别准备告警。
2. 用只属于工作空间 A 的账号登录，确认看不到工作空间 B 的通知。
3. 切换到工作空间 B 的有权限账号，确认可以看到 B 的通知。
4. 直接使用 A 的通知 ID 请求 B 的已读接口，确认返回 404。

## 10. 暂缓项与下一步

本阶段先把“发现问题—通知到人—准确进入处理页”跑通，以下能力可以后续开发：

- 企业微信、钉钉、短信和邮件等外部通知渠道。
- 通知静默时段、值班表、SLA 超时升级和重复提醒策略。
- 通知模板配置、渠道失败重试和发送回执。
- 通知归档、保留周期和个人订阅偏好。

建议下一阶段优先开发“告警 SLA 与升级策略”：给规则配置首次响应时限、处理时限和升级对象，复用本阶段通知表和后台扫描任务，不改造核心聊天执行链路。
