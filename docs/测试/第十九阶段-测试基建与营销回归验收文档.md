# 第十九阶段：测试基建与营销回归验收文档

## 目标

让项目能够在全新、隔离的 PostgreSQL 测试库中完成全部 Django 迁移，并稳定运行营销模块的自动化回归测试。该阶段不新增面向客户的业务页面或接口。

## 修复内容

1. 修复系统管理历史迁移对运行时工作空间模型的依赖。
   - `system_manage.0003` 执行时，`workspace` 表尚未创建；迁移现在只使用该历史时点已存在的模型数据生成默认工作空间权限。
2. 修复模型提供方初始种子数据。
   - 未配置外部 embedding 模型名称时，初始迁移会使用稳定的历史默认值，随后由既有重命名迁移升级为当前模型名称。
3. 修复知识库向量表初始化顺序。
   - 知识库初始迁移在创建 `vector` 类型字段前确保启用 PostgreSQL `vector` 扩展。

## 影响范围

- 修改均位于历史迁移脚本，作用是让新部署、CI 和隔离测试库可以从零初始化。
- 已完成迁移的现有业务库不会重新执行这些迁移，因此不会改写现有业务数据、客户状态或权限记录。
- 旧的本地测试库未被删除或修改；本次验证使用独立临时库，测试结束后由 Django 自动清理。

## 回归覆盖

- 营销客户、批次、执行结果与审批相关逻辑。
- 转化登记、已办理/流失状态回写、归因批次校验和历史保留。
- 非法跨批次归因及绕过转化登记的边界拦截。

## 后续使用方式

后续新增营销功能时，应优先把关键正常路径和边界校验加入 `apps/marketing/tests.py`，并在隔离测试数据库中运行营销测试。这样可以在提交前发现迁移顺序、模型种子和接口回归问题，而不依赖手工页面验收。
