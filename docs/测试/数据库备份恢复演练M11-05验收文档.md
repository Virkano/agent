# PostgreSQL 与文件大对象备份恢复演练 M11-05

验收日期：2026-09-22。结论：**本地隔离恢复演练通过；生产灾备与异地备份仍未验证**。

## 演练边界与方法

本机 Django 实际连接 `127.0.0.1:5432/telecom_ai_agent`，对应 Docker 容器 `telecom-ai-postgres`；源库约 57 MB，启用 `vector` 扩展。业务上传文件由 `knowledge.models.File` 写入 PostgreSQL Large Object，故使用包含大对象的自定义格式 `pg_dump`。本次没有发现独立对象存储桶或需要同步的本地业务上传目录；外部 OSS/对象存储如以后启用，必须另做清单与恢复演练，不能从本次结果推断已覆盖。

脚本先验证本地地址、端口映射、容器运行状态与源库名称；备份写入仅当前用户可读的临时目录，再创建唯一的 `m11_restore_*` 数据库恢复。源库从不作为恢复目标；只删除本次创建的临时库。原始备份包含业务数据，演练后自动删除，仅保存无业务行内容的摘要、备份大小和 SHA-256。

从仓库根目录执行：

```bash
set -e
set -a
source .env.local
set +a
./.venv/bin/python scripts/m11_backup_restore_drill.py --execute
```

不带 `--execute` 只做安全预检。报告见 `output/m11-05/summary.json`，权限为 600。单元测试与静态检查：

```bash
./.venv/bin/python -m unittest scripts.test_m11_backup_restore_drill
./.venv/bin/ruff check scripts/m11_backup_restore_drill.py scripts/test_m11_backup_restore_drill.py
```

## 真实结果

| 校验 | 源库恢复前/后 | 临时恢复库 | 结果 |
| --- | ---: | ---: | --- |
| public 表 | 194 / 194 | 194 | 一致 |
| 大对象 | 13 / 13 | 13 | 一致 |
| `file` 记录 | 18 / 18 | 18 | 一致 |
| 大对象数据块 | 929 / 929 | 929 | 一致 |
| 大对象字节 | 1,887,340 / 1,887,340 | 1,887,340 | 一致 |
| 大对象内容 MD5 一致性指纹 | 一致 | 一致 | 一致，仅用于演练比较，不作安全哈希 |

备份文件 3,842,575 字节，备份约 0.536 秒、恢复约 12.003 秒、完整演练约 15.459 秒。临时库已删除，备份文件未保留；报告中保留 SHA-256 以关联本次输入。以上是本机小体量数据下的实测耗时，**不是生产 RTO/RPO 承诺**。源库在演练前后计数/指纹一致，但并未模拟持续写入、主机故障或跨机恢复。

首次演练因恢复命令未显式指定 `pg_restore -d` 失败，临时库仍被删除；修正并复验通过，详细原因记录在 `.learnings/ERRORS.md` 的 ERR-259。只读诊断文件已删除，没有在日志和文档记录数据库密码或备份内容。

## 待补的生产灾备事项

- 制定带加密、访问控制、异地复制和保留周期的实际备份策略；本演练不保留备份，不能作为持续可恢复能力。
- 在独立环境演练跨主机恢复、应用配置/密钥恢复、`vector` 扩展与版本兼容；验证业务接口和关键文件可读，而不只核对库内计数。
- 明确生产 RPO/RTO 目标、负责人、定期演练频率、失败升级与恢复授权；若接入外部对象存储，增加桶清单、版本、权限与文件内容恢复验证。

因此三同步检查表中的运行期备份恢复控制项仅标记 `PARTIAL`。
