# 第三十二阶段：营销告警处理闭环验收文档

## 1. 本阶段目标

把运营监控页面中的实时“待关注事项”升级为可持续处理的告警工单：告警保存到数据库、相同异常自动去重、处理人可以认领和关闭，并完整保留操作记录。

本阶段不接入短信、邮件、钉钉或企业微信通知；通知渠道将在告警规则和处理闭环稳定后开发。

## 2. 页面入口

登录管理端，切换到目标工作空间，打开左侧“运营监控”。

页面路由：`/admin/marketing-operations`

新增区域：

- “告警处理台”：显示已持久化告警、来源状态、负责人和处理状态。
- “告警处理”抽屉：执行认领、开始处理、关闭、重新打开并查看完整流水。
- “告警规则”抽屉：按工作空间配置开关、告警级别和触发阈值。

## 3. 告警生成规则

系统默认创建五类规则：

| 告警类型 | 默认级别 | 默认阈值 | 处理入口 |
| --- | --- | --- | --- |
| 对话运行错误 | 紧急 | 1 | 对话质检 |
| 发送前检测旁路 | 紧急 | 1 | 对话质检 |
| 触达批次逾期 | 关注 | 1 | 营销任务 |
| 质检记录待复核 | 关注 | 1 | 对话质检 |
| 对话响应偏慢 | 关注 | 1 | 营销任务 |

规则首次访问时为当前工作空间自动补齐，其他已有工作空间无需单独执行初始化脚本。

## 4. 去重和重开逻辑

- 同一工作空间、同一告警类型只有一条告警，不会每次刷新重复建单。
- 来源指标变化时更新告警数量、说明和最近触发时间，并按需记录系统刷新流水。
- 人工关闭后，如果来源仍有异常，普通刷新不会把告警强制改回待处理。
- 来源先恢复或低于阈值后，系统标记为“已恢复”。
- 已关闭告警在来源恢复后再次达到阈值时，系统自动重新打开。
- 处理人也可以手工重新打开已关闭告警。

## 5. 处理状态与操作

```text
待处理 ──认领──> 已认领 ──开始处理──> 处理中 ──填写结论──> 已关闭
   └────────────开始处理──────────────┘                         │
   └────────────────填写结论关闭───────────────────────────────┘
                              已关闭 ──重新打开──> 待处理
```

约束：

- 只有待处理告警可以认领。
- 待处理或已认领告警可以开始处理。
- 关闭告警必须填写处理结论。
- 只有已关闭告警可以重新打开。
- 每次操作都记录操作人、前后状态、说明、指标快照、时间和版本号。

## 6. 后端接口

```http
POST /admin/api/workspace/{workspace_id}/marketing/alert/sync
GET  /admin/api/workspace/{workspace_id}/marketing/alert/{page}/{size}
POST /admin/api/workspace/{workspace_id}/marketing/alert/{alert_id}/handle
GET  /admin/api/workspace/{workspace_id}/marketing/alert-rule
PUT  /admin/api/workspace/{workspace_id}/marketing/alert-rule/{rule_id}
```

同步参数：

```json
{ "days": 7 }
```

处理参数示例：

```json
{ "action": "CLAIM", "note": "" }
{ "action": "START", "note": "开始排查模型调用" }
{ "action": "CLOSE", "note": "已修复模型配置并复测通过" }
{ "action": "REOPEN", "note": "问题再次出现，继续处理" }
```

规则参数示例：

```json
{ "enabled": true, "severity": "CRITICAL", "threshold": 2 }
```

所有查询和操作均校验工作空间；跨工作空间的告警或规则 ID 返回 404。

## 7. 手工验收步骤

### 7.1 生成与去重

1. 在当前工作空间准备一条待复核回答、运行错误、检测旁路、慢响应或逾期批次。
2. 打开“运营监控”，点击“同步告警”。
3. 确认告警处理台出现对应告警。
4. 连续点击两次“同步告警”。
5. 确认同类型告警仍只有一条，指标数量和最近触发时间可以更新。

### 7.2 处理闭环

1. 点击告警行的“处理”。
2. 点击“认领”，确认状态为“已认领”，负责人显示当前登录用户。
3. 点击“开始处理”，确认状态为“处理中”。
4. 不填写结论时，“关闭告警”按钮应不可用。
5. 填写处理结论并关闭，确认状态为“已关闭”。
6. 再次同步告警，确认关闭状态不会因来源仍异常而丢失。
7. 点击“重新打开”，确认状态回到“待处理”。
8. 检查处理记录，确认以上操作按时间倒序完整展示。

### 7.3 规则配置

1. 点击“告警规则”。
2. 修改开关、级别或阈值并保存。
3. 确认提示“告警规则已保存”。
4. 回到告警处理台，确认规则自动重新同步。
5. 当指标低于新阈值或规则关闭时，已有告警的来源状态应显示“已恢复”。

### 7.4 来源跳转

1. 点击告警行的“查来源”。
2. 运行错误、检测旁路、待复核应进入“对话质检”。
3. 逾期批次和慢响应应进入“营销任务”。
4. 确认目标页面和相关接口无 404、500。

## 10. 暂缓项与下一步

暂缓：

- 短信、邮件、钉钉、企业微信通知。
- 定时后台扫描和静默时段。
- 告警升级、值班表和 SLA 超时策略。
- 多人协作评论与附件。

建议下一阶段优先开发“定时告警扫描 + 通知渠道”，先支持站内通知，再按实际部署条件接企业微信或钉钉；大规模改造现有聊天和任务流程仍采用旁路接入，不直接改写核心执行链路。
